Tema 1

Técnicas de análisis de requisitos

¿Por qué priorizar requisitos?

El proceso de análisis de requisitos permite el estudio de las necesidades de los usuarios para definir requisitos del sistema. La priorización es continua — la prioridad de un requisito puede variar a lo largo del proyecto. No decidir sobre la priorización es como no fundamentar las bases sobre las que el equipo de desarrollo va a construir el sistema.

Responsabilidad: La priorización es responsabilidad de los gerentes del proyecto o dueños de producto. Los analistas asesoran y facilitan el proceso para evitar priorizar requisitos con dependencias no resueltas.

1.1

Técnicas de priorización

1.1.1
Técnica de clasificación de lista
Numérica · Secuencial

Consiste en darle un valor numérico a cada requerimiento iniciando por el número 1 y continuando de forma sucesiva. Solo puede existir un número 1, lo cual evita que los interesados quieran que todos los requerimientos tengan prioridad 1; aporta claridad y evita confusiones.

Limitación: Requiere un profundo conocimiento de todos los requerimientos definidos. Aunque el proceso parece simple, se requiere un gran esfuerzo del equipo para situar cada requerimiento en la posición correcta.
1.1.2
Técnica de puntos de historia y valor del negocio
Cuantitativa · Cociente

La priorización se realiza de acuerdo con factores como el esfuerzo y la opinión de los gerentes. Para lograr la priorización se calcula el cociente = valor del negocio ÷ puntos de historia. Los primeros lugares serán los requerimientos más sencillos de resolver y con mayor interés del cliente.

Ejemplo:
R02: valor negocio=8, puntos historia=2 → cociente=4.0 → Prioridad #1
R01: valor negocio=6, puntos historia=3 → cociente=2.0 → Prioridad #2
1.1.3
Técnica urgente
Bidimensional · Escala de colores

Utiliza una tabla de dos dimensiones: urgencia del requerimiento y valor del negocio. La prioridad final se determina multiplicando ambos valores, generando una escala de colores.

🔴 Rojo
Máxima prioridad
🟠 Naranja
Alta prioridad
🟡 Amarillo
Media prioridad
🟢 Verde
Menor prioridad
Ejemplo: R03 con urgencia=9 y valor de negocio=8 → resultado=72 → sector rojo, se aborda primero.
1.1.4
Técnica MoSCoW
Etiquetas · Consenso

Esta técnica se basa en la asignación de etiquetas a cada requerimiento. Los requerimientos se priorizan en orden: primero los M, luego los S, después los C y finalmente los W.

M
Must
Funcionalidad que debe estar. Obligatoria.
S
Should
Funcionalidad que debería estar. Alta prioridad.
C
Could
Funcionalidad que podría estar. Deseable.
W
Won't
Funcionalidad descartada por ahora.
Nota: Si todos los requerimientos se seleccionan como tipo M, automáticamente se transforman en tipo S y se pierde la dinámica de la técnica.
1.1.5
Juicio de expertos
Cualitativa · Subjetiva

Consiste en realizar el proceso de priorización basándose en la opinión del gerente de proyecto, dueño de producto, o de algún experto con conocimientos en la industria asociada al producto a desarrollar.

Cuándo usarla: Funciona bien para proyectos pequeños con un dueño de negocio que tiene mucho conocimiento del problema y la solución. Precaución: Se debe usar con cuidado ya que se basa en una visión sesgada. Combinarla con otras técnicas reduce el sesgo.
1.1.6
Matriz de priorización
Ponderada · Multidimensional

Construye una tabla donde cada requerimiento es valorado en una escala de 0 a 10 para cada dimensión alineada con los objetivos del producto. El valor final resulta de la sumatoria de la multiplicación de cada puntuación por el peso de cada dimensión.

Ejemplo: Dimensiones: Conversión (30%) + Satisfacción del cliente (40%) + Retención (30%).
R01 evalúa 7, 9, 6 → total ponderado = 7×0.3 + 9×0.4 + 6×0.3 = 7.5 → Mayor prioridad
1.3

Descomposición funcional

Estructura top-down

Consiste en definir los requerimientos como una relación de entradas y salidas de un sistema. Normalmente los requerimientos se definen de manera muy general y luego se descomponen en funcionalidades y subfuncionalidades más detalladas — a esta estructura jerárquica se le conoce como top-down.

La descomposición funcional se realiza para identificar y entender los componentes que constituyen un todo. En este proceso es vital identificar las interacciones entre componentes.

1.2

Matriz de trazabilidad

¿Qué es la matriz de trazabilidad?

Herramienta que permite alinear los requisitos del proyecto con los logros de los objetivos. Relaciona cada requerimiento con el entregable solicitado, permitiendo identificar qué resultado se alcanza con cada requisito.

Debe permanecer actualizada a lo largo de todo el ciclo de vida del proyecto. Es clave para el seguimiento y control de cambios.

Identificación
Código único: identificador exclusivo para cada requisito.
Código jerárquico: permite categorizar cada grupo de requisitos.
Descripción: texto explicativo del requerimiento.
Categoría: negocio, interesados, funcional, no funcional, proyecto o calidad.
Control
Versión: importante para el control de cambios.
Estado: activo, cancelado, diferido, agregado, aprobado, asignado o completado.
Fecha de estado: momento de la última modificación.
Responsable: persona encargada del requisito.
Prioridad: escala usada (alta/media/baja o 1-5).
Alineación
Objetivo: meta que pretende alcanzar el requerimiento.
Necesidad de negocio: necesidad que se pretende cubrir.
Grado de cumplimiento: nivel de avance del requisito.
Otras características: cualquier otro campo de valor para la organización.

Ejemplo de estructura de una matriz de trazabilidad:

REQ-002Carrito de compras (depende de REQ-001)FuncionalAltaAsignado1.1L. Gómez
REQ-003Tiempo de respuesta menor a 2 segundosNo funcionalMediaActivo1.0C. Ruiz
REQ-004Generación de reportes en PDFFuncionalBajaDiferido1.2M. López

Cada organización es responsable de adaptar la matriz a sus necesidades.

Tema 2

Especificación de requisitos

Estándares IEEE para requisitos

En esta sección se describen los estándares y técnicas que pueden ser usados por las organizaciones para describir formalmente cada uno de los requisitos del sistema. El IEEE 830-1998 y el más reciente IEEE 29148:2018 son las referencias principales de la industria.

IEEE 830-1998
Estándar para documentos SRS
Presenta un conjunto de prácticas recomendadas para la redacción de un documento de especificación de requerimientos (SRS). Está dividido en secciones que abordan aspectos particulares del sistema.
  • Introducción: ámbito del sistema y propósito
  • Definiciones, acrónimos y abreviaturas
  • Descripción general del producto
  • Perspectiva, funciones y características del producto
  • Características de los usuarios
  • Suposiciones y dependencias
  • Requerimientos específicos: funcionales y no funcionales
  • Otros requisitos
IEEE 29148:2018
Ingeniería de requisitos en el ciclo de vida
Reemplaza IEEE 830, IEEE 1233 e IEEE 1362. Contiene disposiciones para los procesos y productos relacionados con la ingeniería de requisitos a lo largo del ciclo de vida.
  • Requerimientos funcionales: necesidades de los interesados
  • Requerimientos de usabilidad (uso directo)
  • Requerimientos de desempeño: disponibilidad y transacciones
  • Interfaces del sistema: interacción persona-software
  • Operaciones y modos del sistema
  • Características físicas (hardware)
  • Condiciones del ambiente operativas
  • Seguridad del sistema y manejo de la información
  • Políticas, regulación y ciclo de vida
Historia de usuario (ágil)
Estructura base — marcos ágiles
Los marcos ágiles promueven la comunicación oral sobre la documentación exhaustiva. Las historias de usuario son una explicación general e informal de una función del software escrita desde la perspectiva del usuario final.
  • Nombre de la historia de usuario
  • Como [rol del usuario]
  • Quiero [funcionalidad deseada]
  • Para que [beneficio o valor obtenido]
  • Puntos estimados (esfuerzo)
  • Criterios de aceptación
Ejemplo

Historia de usuario — formato y beneficios

Formato estándar de una historia de usuario en marcos ágiles

Formato (Rivadeneira, 2014)

Nombre: HU-012 — Pago en línea con tarjeta

Como cliente registrado,

quiero pagar mi pedido con tarjeta de crédito

para que pueda completar mi compra de forma segura sin salir del sitio.

Puntos estimados: 5

Criterios de aceptación:

✓ El sistema acepta Visa, Mastercard y Amex.
✓ La transacción se confirma en menos de 5 segundos.
✓ Se envía correo de confirmación automáticamente.

Beneficios de las historias de usuario:

  • Se centran en solucionar problemas a usuarios reales, no en documentar funciones técnicas.
  • Permiten la colaboración: como la descripción es corta, el equipo colabora para decidir cómo dar solución.
  • Impulsan la creatividad al fomentar que el equipo piense de forma crítica y creativa.
  • Motivan al equipo: cada historia completada representa un reto y una pequeña victoria.
2.4

Scrum y la especificación de requisitos

El marco Scrum

Scrum está soportado en un proceso de construcción iterativo e incremental evolutivo. Establece el concepto de sprint para referirse a una iteración con tiempos fijos entre 2 y 4 semanas. El artefacto mediante el cual se condensan todos los requerimientos se denomina pila de producto (product backlog).

👥
Equipo de trabajo (Team)
Conformado por desarrolladores, diseñadores, personal de calidad e infraestructura. Estima el esfuerzo (puntos de historia) y construye el producto.
🧭
Scrum Master
Realiza funciones parecidas a las de un director de proyecto. Garantiza que el equipo tenga todas las herramientas y recursos necesarios para su trabajo.
🎯
Product Owner
Representante del cliente. Único encargado de la gestión de requisitos. Prioriza el Product Backlog buscando el mayor retorno de inversión.

Al inicio de cada sprint se realiza el proceso de planeación con tres tareas principales:

01
Estimación de esfuerzo
El equipo de desarrollo estima el valor de esfuerzo requerido para las historias de usuario del Product Backlog en puntos de historia.
02
Selección y Sprint Backlog
Se seleccionan las historias a desarrollar tomando como referencia la prioridad y el esfuerzo. Se genera el Sprint Backlog.
03
Descomposición en tareas
Cada historia de usuario se descompone en tareas y, de ser necesario, se asignan responsables a cada tarea del sprint.
2.5

Kanban y la especificación de requisitos

El tablero Kanban

Kanban es una metodología para gestionar el trabajo que surge del sistema de producción Toyota (TPS) a finales de los años 1940. La herramienta más conocida es el tablero Kanban, que mapea y visualiza el flujo de trabajo dividido en columnas (fases del proceso) y filas (tipos de actividades).

Calidad garantizada
Todo lo que se produce debe salir bien sin márgenes de errores. Prima la calidad sobre la rapidez.
Reducción del desperdicio
Hacer solamente lo justo y necesario, pero hacerlo bien. Minimizar desperdicios sin afectar la producción.
Mejora continua
Proceso constante de experimentación y mejora. Circuitos de realimentación y colaboración del equipo.
Flexibilidad
Se pueden priorizar tareas entrantes según las necesidades del momento. Eliminar interrupciones y gestionar el flujo.
Por hacer
HU-015: Módulo de reportes
HU-016: Exportar a Excel
HU-017: Notificaciones push
En progreso
HU-012: Pago en línea
HU-013: Perfil de usuario
En revisión
HU-010: Carrito de compras
HU-011: Búsqueda avanzada
Completado
HU-001: Registro de usuario
HU-002: Login / Auth
HU-003: Catálogo de productos

Dependiendo del marco de trabajo, varía la forma en que se describen las tareas del tablero. En Scrum, cada tarea se puede describir en formato de historia de usuario.

Glosario

Términos clave

Definiciones de los principales conceptos utilizados en el componente formativo.

Estándar
Referencia, patrón o modelo que es utilizado a nivel general en un determinado ámbito.
Marcos de trabajo ágiles
Conjunto de estándares, metodologías, técnicas, frameworks o guías que rigen un proceso de desarrollo de software basadas en principios y/o valores ágiles. Por ejemplo: Scrum, Lean Software, XP, TDD.
Marcos de trabajo tradicionales
Conjunto de estándares, metodologías, técnicas, frameworks o guías que rigen un proceso de desarrollo de software basadas en el ciclo de vida tradicional. Por ejemplo: RUP, CMMI, ISO 9001.
Metodología
Síntesis de un conjunto de técnicas, métodos y procedimientos que se deben seguir durante el desarrollo de un proyecto.
Pruebas unitarias
Forma de comprobar el correcto funcionamiento de una unidad de código.
Pruebas de integración
Prueba que se ejecuta una vez se aprueban las pruebas unitarias. Busca verificar que el conjunto de fragmentos de código funciona junto de forma correcta.
Técnica
Manera en la que un conjunto de procedimientos es aplicado en una tarea específica, con base en un conocimiento para obtener un resultado específico.
